# Architecture

HomeBox Clipper is a Manifest V3 extension built with [WXT](https://wxt.dev) (Vite-based),
[Vue 3](https://vuejs.org) and strict TypeScript. The code is split into layers that only know each other
through typed contracts: adding a merchant touches neither the HomeBox client nor the interface.

## Overview

```
Popup / Options (Vue)  ──typed messages──▶  Service worker  ──HTTP + API key──▶  Your HomeBox instance
                                                  │
                                                  └──messages (no key)──▶  Script injected into the merchant tab
```

- The **service worker** is the only one to hold the decrypted API key and the only one to talk to HomeBox.
- The **injected script** reads the merchant page and downloads the invoice with the user's session; it
  has access to neither storage nor the settings.
- The **interface** (popup, options) displays, validates and asks; it never receives the key (only a
  masked version).

## Top-level folders of `src/`

| Folder | Role |
|--------|------|
| `assets/` | Static resources used by the code (SVG logo). The extension icons are in `public/icon/`, regenerated by `bun run icons`. |
| `background/` | Service worker: `config/` (storage, encryption, URL rule, handlers), `homebox/` (typed API client), `import/` (orchestration, duplicates, pending imports), `location/` (location list: `handlers.ts`; memory of the last location per instance: `last-location.ts`), `detect.ts` (injection and detection), `router.ts` (message validation and routing). |
| `content/` | Per-merchant extractors (`content/merchants/<merchant>/`): `selectors.ts`, `parse.ts`, `extractor.ts`, `download.ts`, plus the `types.ts` contract and the `registry.ts` registry. No secret and no network access except the invoice download. |
| `entrypoints/` | WXT entry points, deliberately thin: `background.ts`, `popup/`, `options/` and one injectable script per merchant (`amazon-fr.content.ts`). |
| `locales/` | Interface text catalogs (`en.yml`, the default and reference, and `fr.yml`), read by `@wxt-dev/i18n`. See [Translations](Translations.md). |
| `platform/` | Browser API abstraction (`browser`, permissions, i18n): the **only** place that imports the browser API in `src/`, to allow a Firefox port. |
| `shared/` | Types, error codes, internal messages and their validation, PDF utilities, `logger.ts`. |
| `ui/` | Vue components (`components/`, `popup/`, `options/`), theme (`theme.css`, `theme.ts`), text access (`i18n.ts`). |

Outside `src/`: `tests/` (see [Testing-and-fixtures](Testing-and-fixtures.md)), `public/`, `scripts/`,
`wxt.config.ts` (manifest and WXT modules).

## An import in four steps

The HomeBox API (v0.27) does not accept the price, date or seller at creation; hence:

1. `POST /api/v1/entities`: creation (name, description, quantity);
2. `PUT /api/v1/entities/{id}`: purchase information (price, date, seller) and notes; the item is read back
   before the update so as not to overwrite its other fields;
3. `POST /api/v1/entities/{id}/attachments`: one request per document (`multipart/form-data`), of type
   `receipt` for an invoice, `attachment` otherwise;
4. `POST /api/v1/entities/{id}/attachments` for the photo (`type=photo`, `primary=true`), last: its failure
   delays neither the item nor the invoice.

The orchestrator (`src/background/import/orchestrator.ts`) keeps the state of each step. **A successful
step is never replayed and, once the item's identifier is known, the item is never recreated**: a recovery
only performs the remaining steps. On success, the kept purchase data is purged.

### Photo step (`photo-fetch.ts`)

`src/background/import/photo-fetch.ts` retrieves the image with an anonymous `fetch`, in a module
**separate from the HomeBox client** (it never has access to the key). It rechecks the URL against the
merchant's `imageHosts` (`draft.photo.merchantId`), refuses redirects, limits the size (5 MB) and decides
the format from the signature. The orchestrator receives it as a dependency (`fetchPhoto`) and keeps the
step state (`not_requested`, `unavailable`, `pending`, `sending`, `done`, `failed`) in `PendingImport`,
with `photoError` and `photoAttempted`. `sending` is written **before** the POST: on recovery, if an
upload may have gone out, the item is read back and the photo is not sent again if an attachment of type
`photo` already exists. The bytes are never persisted; the same image is downloaded only once per call.

### Orphan imports

The service worker keeps the set of active imports in memory (`activeImports`). On read
(`import/pending`), a `running` import absent from this set no longer has a process behind it: it becomes
`failed` (item not created) or `partial` (item created), marked `orphaned`, and can be retried. All the
imports of a batch are persisted before the first POST. The creation POST is preceded by writing
`createAttempted`; an orphan without an identifier whose POST has started is marked `createUncertain`,
like an import whose POST response was lost (`HOMEBOX_UNREACHABLE`). An explicit HTTP error remains a
certain failure. For an uncertain creation, the recovery first searches for the exact name
(`findDuplicatesByName`, without the order number, which the item does not have before the PUT):
`DUPLICATE_SUSPECTED` if it exists, `DUPLICATE_CHECK_FAILED` if the search fails, in both cases without a
POST. A recovery started while the same one is already running (`activeImports`) returns the current
state without a second execution. The mechanism only covers a service worker stop: `storage.session` is
cleared when the browser closes and when the extension is updated.

Before the import, `duplicate/check` queries HomeBox (`GET /api/v1/entities?q=...`) to spot a probable
duplicate (same order number in the notes, same name).

## Location

`location/list` reads the `GET /entities/tree` tree (without the items), `src/shared/locations.ts`
flattens it into a sorted list of paths (only location-type nodes, bounded depth) and
`lastLocation.resolve` attaches the remembered identifier if it still exists. The `LocationPicker.vue`
component (ARIA combobox, no dependency) only chooses among existing locations. At creation, the location
is sent as **`parentId`** and not as `locationId` (HomeBox refuses an unknown `locationId` with a 422
error); the update `PUT` always sends `parentId` back, otherwise the location would be lost. A location
that disappeared at submission time gives `LOCATION_NOT_FOUND`: nothing is created for that product.

## Internal messaging

Exchanges go through messages declared in `src/shared/messages.ts`: each type has a validator run on
reception (`isMessage`). The router (`src/background/router.ts`):

- answers `BAD_MESSAGE` to any invalid message or one coming from another extension, without running a
  handler;
- reserves the `config/`, `session/`, `detect/`, `duplicate/`, `import/` and `location/` prefixes for the
  extension's pages (popup, options), never for injected scripts;
- converts any handler exception into a visible error, without detail.

Message families: configuration (`config/get|save|test|delete`), session (`session/unlock|lock`),
detection (`detect/run`), locations (`location/list`), duplicates (`duplicate/check`), import
(`import/start|retry|abandon|pending`), extraction in the tab (`amazon/extract`, `amazon/download`) and
progress (`import/progress`). Responses are `Result` values: either a value or an error code from the
catalog (`src/shared/errors.ts`).

## Storage

| Where | What |
|-------|------|
| `storage.local` | Settings (`homeboxConfig`: address, **encrypted** key, masked key, last test), theme (`uiTheme`) and last location per instance (`lastLocationByInstance`: identifiers only, erased with the settings). |
| `storage.session` | Decrypted key (`homeboxUnlocked`) and in-progress imports (`pendingImport:<tab>:<id>`). Memory, cleared when the browser closes. |

Security details: [Security-and-privacy](Security-and-privacy.md).

## Interface texts (i18n)

No visible text is hard-coded in `src/ui/`. The interface calls `t('dotted.key', [values])`
(`src/ui/i18n.ts`), which goes through `src/platform/i18n.ts` (the only access to `browser.i18n`). Error
messages are `errorMessage(code)`, that is `t('error.<CODE>')`. The service worker does not import
`src/ui/`: it calls `getMessage` directly (for example for the note "Amazon.fr order: ...", key
`summary.orderNote`). Keys are typed from the catalog and checked by the tests.

**Language selection.** Two catalogs exist, `src/locales/en.yml` (reference) and `src/locales/fr.yml`,
with the same keys. `default_locale` is `en` in `wxt.config.ts`; the browser serves French when its
interface language is French. In the pages, `uiLanguage()` (`src/ui/i18n.ts`) derives the language from
the browser's interface language (`fr` for `fr`, `fr-CA`..., otherwise `en`) and drives the `lang`
attribute and `formatDate`. Parity between the catalogs is enforced: see [Translations](Translations.md).

## Rules that structure the code

- A merchant's DOM selectors live only in its `selectors.ts`, with several fallback selectors per field;
  the failure of one field does not interrupt the others.
- The HomeBox client is an isolated module, typed from the API, independent of the interface and of the
  merchants.
- No `console.*` outside `src/shared/logger.ts` (ESLint rule).
- Minimal permissions and a single build; any change to the manifest must be justified in the pull request.

The full principles are in the project constitution, summarized in the
[contributing guide](https://github.com/Foufou-exe/homebox-clipper/blob/main/CONTRIBUTING.md). To extend
the code: [Adding-a-merchant](Adding-a-merchant.md).
