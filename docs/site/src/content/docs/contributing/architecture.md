**Who this page is for**: contributors who need to understand how the code is organized before changing
it. Reference page: read the section you need. To run the project first, see
[Set up the project](/homebox-clipper/contributing/development-setup/).

HomeBox Clipper is a Manifest V3 extension built with [WXT](https://wxt.dev) (Vite-based),
[Vue 3](https://vuejs.org) and strict TypeScript. The code is split into layers that only know each other
through typed contracts: adding a merchant touches neither the HomeBox client nor the interface.

## Overview

```
Popup / Options (Vue)  ──typed messages──▶  Service worker  ──HTTP + API key──▶  Your HomeBox instance
                                                  │
                                                  └──messages (no key)──▶  Script injected into the merchant tab
```

- The **service worker** is the only one to hold the decrypted API key and the only one to talk to HomeBox.
- The **injected script** reads the merchant page and downloads the invoice with the user's session; it
  has access to neither storage nor the settings.
- The **interface** (popup, options) displays, validates and asks; it never receives the key (only a
  masked version).

## Top-level folders of `src/`

| Folder | Role |
|--------|------|
| `assets/` | Static resources used by the code (SVG logo). The extension icons are in `public/icon/`, regenerated by `bun run icons`. |
| `background/` | Service worker: `config/` (storage, encryption, URL rule, handlers), `homebox/` (typed API client), `import/` (orchestration, duplicates, pending imports), `location/` (location list: `handlers.ts`; memory of the last location per instance: `last-location.ts`), `history/` (local import history: pure projection `entry.ts`, AES-GCM encryption `history-crypto.ts`, encrypted storage and pruning `history-store.ts`, `history/*` handlers), `detect.ts` (injection and detection), `router.ts` (message validation and routing). |
| `content/` | Per-merchant extractors (`content/merchants/<merchant>/`): `selectors.ts`, `parse.ts`, `extractor.ts`, `download.ts`, plus the `types.ts` contract and the `registry.ts` registry. No secret and no network access except the invoice download. |
| `entrypoints/` | WXT entry points, deliberately thin: `background.ts`, `popup/`, `options/` and one injectable script per merchant (`amazon.content.ts`, shared by the eight Amazon stores). |
| `locales/` | Interface text catalogs (`en.yml`, the default and reference, and `fr.yml`), read by `@wxt-dev/i18n`. See [Translations](/homebox-clipper/contributing/translations/). |
| `platform/` | Browser API abstraction (`browser`, permissions, i18n): the **only** place that imports the browser API in `src/`, to allow a Firefox port. |
| `shared/` | Types, error codes, internal messages and their validation, PDF utilities, `logger.ts`. |
| `ui/` | Vue components (`components/`, `popup/`, `options/`), theme (`theme.css`, `theme.ts`), text access (`i18n.ts`). |

Outside `src/`: `tests/` (see [Testing-and-fixtures](/homebox-clipper/contributing/testing-and-fixtures/)), `public/`, `scripts/`,
`wxt.config.ts` (manifest and WXT modules).

## An import in four steps

The HomeBox API (v0.27) does not accept the price, date or seller at creation; hence:

1. `POST /api/v1/entities`: creation (name, description, quantity);
2. `PUT /api/v1/entities/{id}`: purchase information (price, date, seller) and notes; the item is read back
   before the update so as not to overwrite its other fields;
3. `POST /api/v1/entities/{id}/attachments`: one request per document (`multipart/form-data`), of type
   `receipt` for an invoice, `manual` for a manual, `warranty` for a warranty, `attachment` otherwise (delivery
   note, order document). If the instance answers 422 to `manual` or `warranty`, the same file is sent once more
   as `attachment` and the popup says so;
4. `POST /api/v1/entities/{id}/attachments` for the photo (`type=photo`, `primary=true`), last: its failure
   delays neither the item nor the invoice.

The orchestrator (`src/background/import/orchestrator.ts`) keeps the state of each step. **A successful
step is never replayed and, once the item's identifier is known, the item is never recreated**: a recovery
only performs the remaining steps. On success, the kept purchase data is purged.

### Entity type of the imported items (spec 023)

The summary reads the item types of the target instance once (`entity-type/list`, `GET /api/v1/entity-types`,
read-only, extension pages only) and shows a native « Type » select per product when there are at least two
non-location types. The service worker works out the server default (the oldest non-location type, the one HomeBox
applies when none is sent) and the last type used on the instance (`lastEntityTypeByInstance`, erased when the type
is gone). `ImportDraft.entityTypeId` is present only for a type other than the server default, never with
`complete`; `createEntity` and `createFromTemplate` add `entityTypeId` to the body only when it is present, so a draft
without it produces exactly the requests of before. After a definite creation failure with a type, the types are read
once more: a type that is gone gives `ENTITY_TYPE_NOT_FOUND`. After a batch that created an item, the type of the last
created product is remembered (`null` erases the memory). A 404, an error or a single type hides the select.

### Import with a HomeBox item template (spec 018)

When a template is chosen for a product (`ImportDraft.template`), the orchestrator follows a template path,
selected only by `draft.template` (without a template, the code, the requests and the persisted states are
unchanged: the `orchestrator-call-sequence` snapshot is never regenerated):

1. before anything is persisted, each distinct template of the batch is read again (`GET /api/v1/templates/{id}`)
   and its SHA-256 fingerprint compared with the one confirmed: deleted gives `TEMPLATE_NOT_FOUND`, changed gives
   `TEMPLATE_CHANGED`, and nothing is created for any product of the batch;
2. `POST /api/v1/templates/{id}/create-item` with exactly `{ name, description?, quantity, parentId }` replaces
   `POST /api/v1/entities` (a location is required; never a fallback to `POST /entities`);
3. a single `PUT /api/v1/entities/{id}` carries the purchase data, the template values (insured, manufacturer,
   model number, the warranty shown), the custom fields paired by `(name, type)` (foreign fields sent back as they
   are) and the tags; a default tag of a template is never created (`noCreate`);
4. the extension reads the item again (`GET /api/v1/entities/{id}`) and compares every confirmed field: a gap
   fails the « template fields » step (`steps.templateFields`, `TEMPLATE_FIELDS_FAILED`), the item is kept and
   the step can be retried alone, without creating the item again.

A retry before creation re-checks the template the same way; once the item exists, the template is never read
again. The template list is unavailable (`TEMPLATES_UNAVAILABLE`) or unsupported by the instance
(`TEMPLATES_UNSUPPORTED`, 404): an import without template stays possible.

### Order fields as HomeBox custom fields (spec 019)

When the option « Save the order as custom fields » is on for the target instance, each confirmed draft carries
`ImportDraft.orderFields` (1 to 3 text fields: order number, merchant, order page address, with the names of the
settings of that instance). The orchestrator follows the order-fields path only when this key exists (option off:
no new code runs, the requests and the persisted states are unchanged, the `orchestrator-call-sequence` snapshot is
never regenerated):

1. the existing purchase `PUT /api/v1/entities/{id}` also carries the order fields in `fields` (no extra write): a
   text field of the same name already on the item (from a template, or a previous attempt) is updated in place,
   every other custom field is sent back as it is (#109); the notes stay exactly those of today;
2. a definite refusal of this PUT (known HTTP status other than 401/403) is sent again once without the order
   fields, from the same state read before, so the purchase data, notes, tags and template fields are never lost;
3. after a PUT carrying the order fields, the extension reads the item again (`GET /api/v1/entities/{id}`, the same
   read as the template check when there is a template) and checks that each order field is present exactly once
   with its value: a gap or a refusal fails the « order fields » step (`steps.orderFields`, `ORDER_FIELDS_FAILED`),
   the item is kept and the step can be retried alone, with the names and values confirmed at the start.

The names of the existing custom fields are read for the suggestions of the settings only
(`GET /api/v1/entities/fields`, unlocked, the instance of the message only; never the values); unreadable gives
`FIELD_NAMES_UNAVAILABLE`.

### Order page as an external link (spec 025)

When the option « Add a link to the order page » is on for the target instance and the box of a product is ticked,
the confirmed draft carries `ImportDraft.orderLink: true` (absent otherwise, never `false`; the address is the
draft `pageUrl`, http(s) without credentials). `import/start` refuses it (`BAD_MESSAGE`, before any request) when the
option is off for the target, or on a draft that completes an existing item. The orchestrator adds the step
`steps.orderLink` only when the key exists, so without the option the requests, the persisted states and the
`orchestrator-call-sequence` snapshot (never regenerated) are unchanged:

1. after the photo, one `POST /api/v1/entities/{id}/attachments/external` with the body
   `{ source_type: "link", external_id: <address>, title, attachment_type: "attachment" }` (HomeBox accepts only the
   source type `link`, and an http(s) address without credentials; it does not de-duplicate links);
2. `orderLinkAttempted` is written before the POST; a resume of an attempted step reads the item again
   (`GET /api/v1/entities/{id}`) and looks for an attachment of type `link/url` with the same path: found, the step is
   done without sending; not found, the POST is sent; unreadable, nothing is sent. The extension never creates a
   second link;
3. a failure leaves the import partial (`steps.orderLink: 'failed'`, `ORDER_LINK_FAILED`), after the photo and before the
   tags in the order of the reported errors, and never stops the other steps. A 404 of the route followed by a readable
   item is `ORDER_LINK_UNSUPPORTED` (instance without external links).

The setting is `storage.local.orderLinkByInstance` (`{ [instanceId]: { enabled } }`, erased with the instance or the
settings), read and written by `order-link/get` and `order-link/set`. The completion path of spec 021 never runs the
step. Neither the address, nor the title, nor the item identifier is logged (endpoint template, status and duration
only).

### Manufacturer, model and serial number (spec 027)

The injected script (`amazon/extract`) runs `extractWithLookups` (`src/content/merchants/extract-all.ts`): the page
extraction, then, in parallel, `resolveDocuments` and the optional `resolveProductIdentifiers` of the merchant
contract. For Amazon, `src/content/merchants/amazon/product-details.ts` reads `<origin>/dp/<ASIN>` for each
distinct ASIN (10 at most, 3 at a time, 8 s each and 10 s for the whole lookup, 5 MB counted on the streamed body,
`credentials: 'omit'`, `referrerPolicy: 'no-referrer'`,
final address on the same origin, HTML only) and reads the detail rows (`SELECTORS.productDetailRow`, labels
`productDetailLabels` of `page-locales.ts`). Each `DetectedProduct` then carries `manufacturer` and `modelNumber`
(`Field<string>`) only when its page was read (`not_found`: read, no such row); a product whose page was not read
(no ASIN, beyond 10, failure, budget exceeded) has neither field, and no notice is shown. Never an error.

The summary shows them in `IdentifiersSection.vue` with an empty serial number; the confirmed draft carries
`ImportDraft.identifiers` (`{ manufacturer?, modelNumber?, serialNumber? }`, clean, non-empty, 255 bytes at most;
absent without any value, never with `complete`, the serial number only with a template). No new step and no new
request: `purchaseBase` adds `identifiersPatch(draft.identifiers, current)` to the purchase PUT, each value only
when the item read or created has none. Without identifiers, the PUT and the `orchestrator-call-sequence` snapshot
are unchanged.

### Target collection (spec 024)

`collectionByInstance` (`storage.local`) holds, per instance, the chosen collection (`chosen`, or none: the default
collection of the key) and the one last read (`seen`, with `several`). `configStore.getCredentials` adds `tenant` only
when a collection is chosen; the client then sends `X-Tenant: <id>` on every authenticated request of this instance
(never on the public `GET /status`, never in the URL). Without a chosen collection no header is sent and the requests
are unchanged (`orchestrator-call-sequence` and its snapshot untouched). The messages `instance/collections` and
`instance/set-collection` read `GET /api/v1/groups/all` and `GET /api/v1/groups` **without** `X-Tenant` (a lost
collection must not prevent choosing another one). A 403 with the header is `COLLECTION_UNAVAILABLE`, never retried
without it (no fallback PUT in the orchestrator either; duplicates report it too); an unreadable list is
`COLLECTIONS_UNAVAILABLE`. Each entry stores the address it was read on: after an address change it no longer applies
(no second write). Writes are compare-and-write inside the configuration write queue. An unreadable entry makes
`getCredentials` fail with `COLLECTION_UNAVAILABLE` (never the default collection); the discovery reads use
`getKeyCredentials`. An import keeps the collection it started with (`PendingImport.collection`): every resume uses it,
whatever the current setting, and the result names it. The summary names the collection from the view
(`InstanceView.collection`), without any request.

### Completing an existing item (spec 021)

In the duplicate window, a product can be set to **Complete** an item found (certain duplicate or similar item)
instead of creating one. The popup then sends `import/complete-preview` (`{ instanceId, entityId, draft }`) for each
chosen product: the service worker reads the item on the target instance (`GET /api/v1/entities/{id}`; 404 →
`ITEM_NOT_FOUND`) and the pure module `src/background/import/completion.ts` computes the possible changes
(`planCompletion`: documents whose title is not on the item yet, the photo, missing tags, empty purchase and warranty
values, absent order custom fields, the notes line). The answer holds only keys, the item name and its quantity:
nothing else of the item reaches the popup, and nothing is stored or logged.

After the confirmation, the same `import/start` carries every product; a completed product carries
`ImportDraft.complete` (`entityId`, `itemName`, confirmed `keys`, optional `quantityIncrease`), never a template, and
`location: null`. The orchestrator never creates it: its import starts with `entityId` set and the creation step
done. At each run (first one and resumes), it reads the item again, intersects the confirmed keys with what is still
applicable (`completionPatch`; the others go to `completion.skipped`), then sends **a single PUT** built by
`preservingUpdate` in `src/background/homebox/client.ts`: every property of the item read, including the tags, the
location, the custom fields and the sale details (`soldDate`, `soldTo`, `soldPrice`, `soldNotes`) and
`syncChildEntityLocations` that `entityOutToUpdate` (creation path, unchanged) does not copy, plus the additions
only. No PUT is sent when nothing is left to write (`completion.noChange`). Documents are attached by the existing
step, except those whose title is already on the item (`completion.present`); the photo is sent with `primary=true`
only when the item has no primary photo. Resume guards: the number of photos is remembered before the photo POST
(`completion.photoCountBefore`), and the quantity base and target are remembered before the PUT
(`completion.quantityBase`, `completion.quantityTarget`), so a resume never sends a document, the photo or the
quantity increase twice. The history entry gets `completed: true`.

### Photo step (`photo-fetch.ts`)

`src/background/import/photo-fetch.ts` retrieves the image with an anonymous `fetch`, in a module
**separate from the HomeBox client** (it never has access to the key). It rechecks the URL against the
merchant's `imageHosts` (`draft.photo.merchantId`), refuses redirects, limits the size (5 MB) and decides
the format from the signature. The orchestrator receives it as a dependency (`fetchPhoto`) and keeps the
step state (`not_requested`, `unavailable`, `pending`, `sending`, `done`, `failed`) in `PendingImport`,
with `photoError` and `photoAttempted`. `sending` is written **before** the POST: on recovery, if an
upload may have gone out, the item is read back and the photo is not sent again if an attachment of type
`photo` already exists. The bytes are never persisted; the same image is downloaded only once per call.

### Orphan imports

The service worker keeps the set of active imports in memory (`activeImports`). On read
(`import/pending`), a `running` import absent from this set no longer has a process behind it: it becomes
`failed` (item not created) or `partial` (item created), marked `orphaned`, and can be retried. All the
imports of a batch are persisted before the first POST. The creation POST is preceded by writing
`createAttempted`; an orphan without an identifier whose POST has started is marked `createUncertain`,
like an import whose POST response was lost (`HOMEBOX_UNREACHABLE`). An explicit HTTP error remains a
certain failure. For an uncertain creation, the recovery first searches for the exact name
(`findDuplicatesByName`, without the order number, which the item does not have before the PUT):
`DUPLICATE_SUSPECTED` if it exists, `DUPLICATE_CHECK_FAILED` if the search fails, in both cases without a
POST. A recovery started while the same one is already running (`activeImports`) returns the current
state without a second execution. The mechanism only covers a service worker stop: `storage.session` is
cleared when the browser closes and when the extension is updated.

Before the import, `duplicate/check` queries HomeBox for each selected product and returns
`{ matches, similar, moreSimilar, incomplete }`: at most 4 searches per product, in parallel
(`GET /api/v1/entities?q=...`): the order number in quotes (certain duplicate: same order number in the notes,
same name, unchanged) and at most 3 significant words of the name (`pageSize=50`). The closeness of the names
(FR-004 of spec 015) is computed in the service worker by the pure module `src/shared/similarity.ts`; HomeBox
only supplies candidates. `similar` holds at most 5 items, never a certain duplicate; `incomplete` means some
searches failed (product not checked). The recovery of an uncertain creation keeps `findDuplicatesByName`
(exact name). When the order-fields option is on for the target instance (read from the instance setting by the
service worker; the `duplicate/check` message is unchanged), and the order number is not empty, a fifth request
runs in parallel: `GET /api/v1/entities?fields=<name>=<number>` (exact match on the order-number custom field). An
item found only by this filter, with the same name, is confirmed by `GET /api/v1/entities/{id}` (at most 5 reads,
otherwise `incomplete`), because a server may ignore the filter. Nothing is stored and nothing personal is logged.

## Location

`location/list` reads the `GET /entities/tree` tree (without the items), `src/shared/locations.ts`
flattens it into a sorted list of paths (only location-type nodes, bounded depth) and
`lastLocation.resolve` attaches the remembered identifier if it still exists. The `LocationPicker.vue`
component (ARIA combobox, no dependency) only chooses among existing locations. At creation, the location
is sent as **`parentId`** and not as `locationId` (HomeBox refuses an unknown `locationId` with a 422
error); the update `PUT` always sends `parentId` back, otherwise the location would be lost. A location
that disappeared at submission time gives `LOCATION_NOT_FOUND`: nothing is created for that product.

## Internal messaging

Exchanges go through messages declared in `src/shared/messages.ts`: each type has a validator run on
reception (`isMessage`). The router (`src/background/router.ts`):

- answers `BAD_MESSAGE` to any invalid message or one coming from another extension, without running a
  handler;
- reserves the `config/`, `session/`, `detect/`, `duplicate/`, `import/`, `location/`, `history/`,
  `update/`, `tag/`, `instance/`, `entity-type/` and `template/` prefixes for the extension's pages (popup, options), never for injected scripts;
- calls the activity hook of the automatic lock (`src/background/config/auto-lock.ts`) for each accepted
  message from an extension page, before the handler;
- converts any handler exception into a visible error, without detail.

Message families: configuration (`config/get|delete`), HomeBox instances
(`instance/add|update|rename|test|delete`), session
(`session/unlock|lock|open|get-policy|set-policy|change-passphrase`), updates (`update/state|dismiss|apply`, handled in
`src/background/update/`),
detection (`detect/run`), locations (`location/list`), HomeBox item types (`entity-type/list`, read-only, `src/background/entity-types/`), HomeBox tags (`tag/list`, read-only, `src/background/tags/`),
HomeBox item templates (`template/list`, `template/get`, `template/check`, `template/get-default`,
`template/set-default`, `src/background/templates/`: read-only on the templates, never a template write;
`template/get-default` needs neither the network nor the key), order fields as HomeBox custom fields
(`order-fields/get`, `order-fields/set`: the setting of one instance, readable and writable while locked, neither the
network nor the key; `order-fields/names`: the names of the existing custom fields, unlocked,
`src/background/order-fields/`), the order page link (`order-link/get`, `order-link/set`: the setting of one instance, readable and writable while locked, neither the network nor the key; `src/background/order-link/`), the target collection (`instance/collections`, `instance/set-collection`,
unlocked, `src/background/collections/`), duplicates (`duplicate/check`), import
(`import/start|retry|abandon|pending`), extraction in the tab (`amazon/extract`, `amazon/download`) and
progress (`import/progress`). Responses are `Result` values: either a value or an error code from the
catalog (`src/shared/errors.ts`).

Every message that contacts HomeBox names its target instance: `location/list`, `tag/list`, `duplicate/check`
and `import/start` carry an `instanceId` (validated, 1 to 64 characters); there is no fallback to a default
instance. Each handler builds its HomeBox client once, from `configStore.getCredentials(instanceId)` (errors in
this order: `NOT_CONFIGURED`, `INSTANCE_NOT_FOUND`, `LOCKED`, `KEY_UNREADABLE`, `PERMISSION_DENIED`).
`import/retry` carries no target: it reads `instanceId` from the interrupted import, set by the import handler
(the `store` and `notify` given to the orchestrator are wrapped). The orchestrator itself knows nothing about
instances and stays unchanged (`src/background/import/orchestrator.ts`); its contract snapshot
(`tests/contract/__snapshots__/orchestrator-call-sequence.test.ts.snap`) is never regenerated.

## Storage

| Where | What |
|-------|------|
| `storage.local` | HomeBox instances (`homeboxInstances`: the vault `{ kdf, iterations, salt, check, historyKey }` and 1 to 10 instances `{ id, name, baseUrl, key, maskedKey, lastCheck }`, each key **encrypted** with the address of its instance as associated data), the instance of the last successful import (`lastInstanceId`), theme (`uiTheme`) and last location per instance (`lastLocationByInstance`, indexed by instance id: identifiers only, erased with the instance or the settings). Import history: one **encrypted** envelope `{ v, iv, ct, inst? }` per product (`importHistory:<id>`), where `inst` is the id of its instance in clear (outside the ciphertext, not authenticated), and its setting (`importHistorySettings`); the history key is sealed in the vault. Automatic lock setting (`lockSettings`), last update notice (`updateNotice`) and automatic-tag setting (`tagSettings`). Default item template per instance (`defaultTemplateByInstance`: `{ [instanceId]: { id, name } }`, erased with the instance or the settings, spec 018). Order-fields setting per instance (`orderFieldsByInstance`: `{ [instanceId]: { enabled, names: { orderNumber, merchant, orderUrl } } }`, erased with the instance or the settings, spec 019), the link setting of each instance (`orderLinkByInstance`: `{ [instanceId]: { enabled } }`, erased with the instance or the settings, spec 025). Last item type used per instance (`lastEntityTypeByInstance`: `{ [instanceId]: typeId }`, identifiers only, erased with the instance or the settings, spec 023). |
| `storage.session` | Decrypted keys by instance and open history key (`homeboxUnlocked`, `{ v: 2, keys, historyKey }`; a former `{ apiKey }` is read as the key of the single instance), last activity (`homeboxActivity`, for the inactivity lock), version ready to install (`updateReady`) and in-progress imports (`pendingImport:<tab>:<id>`). Memory, cleared when the browser closes. |

The vault and the instances live in `src/background/config/instance-store.ts` (validated reads, a single write
queue) and `src/background/config/vault-crypto.ts` (one PBKDF2 derivation per operation opens or seals every key;
the vault key is never stored nor put in the session). The former single configuration (`homeboxConfig`, up to
0.6.0) is migrated at start-up into the first instance (id `migrated`): the migration is idempotent and can be
resumed after an interruption, asks for no passphrase and no permission, and while it has not succeeded a
fallback view reads `homeboxConfig`. Going back to a version before multi-instance support (a **downgrade**) is
not supported: such a version does not read `homeboxInstances`.

Security details: [Security-and-privacy](/homebox-clipper/security-and-privacy/).

## Interface texts (i18n)

No visible text is hard-coded in `src/ui/`. The interface calls `t('dotted.key', [values])`
(`src/ui/i18n.ts`), which goes through `src/platform/i18n.ts` (the only access to `browser.i18n`). Error
messages are `errorMessage(code)`, that is `t('error.<CODE>')`. The service worker does not import
`src/ui/`: it calls `getMessage` directly (for example for the note "Amazon.de order: ...", key
`summary.orderNote`). Keys are typed from the catalog and checked by the tests.

**Language selection.** Two catalogs exist, `src/locales/en.yml` (reference) and `src/locales/fr.yml`,
with the same keys. `default_locale` is `en` in `wxt.config.ts`; the browser serves French when its
interface language is French. In the pages, `uiLanguage()` (`src/ui/i18n.ts`) derives the language from
the browser's interface language (`fr` for `fr`, `fr-CA`..., otherwise `en`) and drives the `lang`
attribute and `formatDate`. Parity between the catalogs is enforced: see [Translations](/homebox-clipper/contributing/translations/).

## Rules that structure the code

- A merchant's DOM selectors live only in its `selectors.ts`, with several fallback selectors per field;
  the failure of one field does not interrupt the others.
- The HomeBox client is an isolated module, typed from the API, independent of the interface and of the
  merchants.
- No `console.*` outside `src/shared/logger.ts` (ESLint rule).
- Minimal permissions and a single build; any change to the manifest must be justified in the pull request.

The full principles are in the project constitution, summarized in the
[contributing guide](https://github.com/Foufou-exe/homebox-clipper/blob/main/CONTRIBUTING.md). To extend
the code: [Adding-a-merchant](/homebox-clipper/contributing/adding-a-merchant/).
